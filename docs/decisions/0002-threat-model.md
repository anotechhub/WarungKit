# ADR 0002 — Threat Model WarungKit

**Status:** Accepted
**Tanggal:** 2026-07-04
**Proyek:** WarungKit
**Terkait:** `docs/decisions/0001-architecture-baseline.md`, `CLAUDE.md`, `docs/WarungKit_BRD_Technical_Blueprint_v1.0.pdf` (Section 8)

---

## Tujuan

Dokumen ini memetakan setiap ancaman keamanan yang relevan untuk MVP webinar WarungKit ke kontrol teknis nyata yang harus diimplementasikan. Setiap baris tabel harus dapat diverifikasi dengan bukti konkret (test, review manual, atau observasi konfigurasi) — bukan hanya klaim.

**Catatan penting tentang verifikasi Mayar:** Dokumen ini **tidak mengasumsikan mekanisme signature webhook Mayar tertentu** (mis. HMAC dengan header signature spesifik) kecuali telah diverifikasi langsung dari dokumentasi resmi Mayar yang berlaku saat implementasi. Kontrol kepercayaan utama yang digunakan di sini adalah **verifikasi status invoice server-side** — Worker memanggil balik Mayar API untuk mengonfirmasi status pembayaran yang sebenarnya, alih-alih hanya mempercayai isi payload webhook atau header apa pun di dalamnya. Jika Mayar ternyata menyediakan mekanisme signature resmi, itu dapat ditambahkan sebagai lapisan pertahanan tambahan di P8, tidak menggantikan verifikasi server-side ini.

## Tabel Threat Model

| ID | Asset / Area | Skenario Ancaman | Vektor Serangan | Dampak | Mitigasi Wajib | Bukti Verifikasi | Prioritas |
|---|---|---|---|---|---|---|---|
| T-01 | Integritas harga | Pengguna mengubah harga produk melalui dev tools browser sebelum checkout dikirim. | Manipulasi request body di client (DevTools, proxy, curl). | Kerugian finansial — produk dibeli dengan harga jauh di bawah harga asli. | Backend hanya menerima `productId` dari klien; harga selalu diresolusi ulang dari `products.price_idr` di database. Body request tidak pernah dipercaya untuk field harga. | Integration test: checkout dengan harga palsu di body tetap menghasilkan order dengan `amount_idr` sesuai database, bukan payload klien. | Tinggi |
| T-02 | Kerahasiaan `MAYAR_API_KEY` | Kunci API Mayar bocor lewat kode frontend, log, atau commit Git. | Hardcoded secret, commit tidak sengaja, atau environment variable frontend yang salah konfigurasi. | Penyerang dapat membuat/memanipulasi invoice atas nama WarungKit; kerugian finansial dan reputasi. | `MAYAR_API_KEY` hanya hidup sebagai Cloudflare Worker secret (`wrangler secret put`); tidak pernah ada di kode, `.env.example`, atau bundle frontend. | Secret scan riwayat Git bersih; inspeksi bundle frontend dan network tab tidak menunjukkan kunci ini. | Tinggi |
| T-03 | Kerahasiaan `SUPABASE_SERVICE_ROLE_KEY` | Service role key Supabase bocor ke browser atau riwayat Git. | Sama seperti T-02, atau kesalahan penempatan variabel di frontend build. | Akses penuh baca/tulis ke seluruh database tanpa batasan RLS — dampak lebih besar dari T-02. | Service role key hanya sebagai Worker secret; hanya dipakai oleh repository layer backend, tidak pernah diteruskan ke klien. | Secret scan riwayat Git bersih; review kode memastikan key hanya diimpor di modul server-side. | Tinggi |
| T-04 | Kontrol akses API (CORS) | Origin yang tidak dikenal memanggil API publik WarungKit langsung. | Request lintas origin dari domain yang tidak diizinkan, memanfaatkan CORS yang longgar. | Penyalahgunaan API dari domain lain, potensi pencurian data atau abuse checkout. | `ALLOWED_ORIGINS` sebagai allowlist eksplisit; tidak ada wildcard (`*`) di environment mana pun yang dipakai demo. | Test otomatis: request dari origin di luar allowlist ditolak oleh middleware CORS. | Tinggi |
| T-05 | Akses langsung database sensitif | Browser mengakses tabel `orders`/`payment_events`/`checkout_idempotency` langsung via Supabase client-side. | Penggunaan anon key Supabase langsung dari browser tanpa melalui backend. | Kebocoran data pelanggan lain; potensi manipulasi status order langsung di database. | RLS aktif di seluruh tabel; tidak ada policy anonim permisif untuk tabel sensitif; seluruh akses data sensitif hanya lewat repository layer backend. | Test RLS: query dari anon key ditolak untuk `orders`, `payment_events`, `checkout_idempotency`. | Tinggi |
| T-06 | Enumerasi order | Penyerang menebak `orderId` berurutan/predictable untuk melihat order pelanggan lain. | Iterasi ID pada endpoint `GET /api/orders/:orderId`. | Kebocoran data pelanggan (nama, status pembayaran) milik order lain. | Endpoint status order mewajibkan receipt token yang tidak bisa ditebak; ID order menggunakan UUID, bukan sequential integer; tanpa token yang benar, endpoint tidak mengembalikan data. | Test: request `GET /api/orders/:orderId` tanpa token/dengan token salah menghasilkan 403/404 generik tanpa membocorkan keberadaan order. | Sedang |
| T-07 | Status pembayaran palsu via redirect | Pengguna membuka URL redirect sukses secara manual (tanpa membayar) dan berharap status berubah menjadi paid. | Manipulasi parameter query pada URL status/redirect. | Klaim pembayaran palsu; berpotensi merugikan proses fulfilment jika dipercaya. | Status "paid" hanya dibaca dari database setelah verifikasi server-side; parameter query redirect tidak pernah digunakan sebagai sumber status di halaman status pembayaran (keputusan Q-02, lihat `docs/PROJECT_CHECKLIST.md`). | Test manual: mengubah parameter query redirect (mis. `?status=paid`) tidak mengubah tampilan status tanpa konfirmasi backend. | Tinggi |
| T-08 | Replay webhook | Event webhook yang sama dikirim ulang berkali-kali (baik oleh provider yang retry maupun pihak jahat yang merekam lalu memutar ulang request). | Pengiriman ulang payload webhook yang identik ke `POST /api/webhooks/mayar`. | Jika tidak ditangani, dapat memicu efek samping ganda (misalnya notifikasi berulang, atau proses fulfilment berjalan dua kali). | Setiap event disimpan dengan hash/id unik di `payment_events`; event dengan hash/id yang sama diproses sebagai no-op pada percobaan kedua dan seterusnya. | Test webhook: mengirim event yang identik dua kali menghasilkan hanya satu transisi status; percobaan kedua tidak membuat efek samping tambahan. | Tinggi |
| T-09 | Webhook spoofing / payload tidak valid | Pihak yang tidak berwenang mengirim request palsu langsung ke endpoint webhook publik. | Request langsung ke `POST /api/webhooks/mayar` dengan payload rekaan, tanpa melalui Mayar sungguhan. | Jika dipercaya mentah-mentah, penyerang bisa memicu order menjadi `paid` tanpa pembayaran nyata. | Payload webhook divalidasi terhadap struktur yang diharapkan; status pembayaran selalu diverifikasi ulang server-side langsung ke Mayar API sebelum mengubah status order — payload webhook itu sendiri tidak pernah menjadi otoritas akhir. | Test webhook: payload dengan struktur tidak valid ditolak/dicatat sebagai anomali tanpa mengubah status order; test memverifikasi bahwa perubahan status selalu melalui pemanggilan verifikasi ke Mayar API. | Tinggi |
| T-10 | Duplikasi checkout | Pengguna klik ganda tombol "Beli Sekarang" atau retry otomatis dari jaringan tidak stabil. | Pengiriman ulang request `POST /api/checkout` yang sama dari klien. | Order ganda untuk transaksi yang sama; kebingungan pelanggan dan potensi pembayaran ganda. | Setiap checkout mewajibkan `idempotencyKey`; request dengan key yang sama mengembalikan response order yang sudah ada, bukan membuat order baru (tabel `checkout_idempotency`). | Integration test: dua request checkout dengan idempotency key sama hanya menghasilkan satu order di database. | Tinggi |
| T-11 | Duplikasi pembuatan invoice Mayar | Retry pada langkah pembuatan invoice menghasilkan lebih dari satu invoice untuk order yang sama. | Kegagalan jaringan sementara antara Worker dan Mayar yang memicu retry logic tanpa pengecekan status sebelumnya. | Kebingungan pelanggan (dua link pembayaran berbeda untuk satu order), potensi pembayaran ganda. | Pembuatan invoice terjadi hanya setelah order `pending` berhasil dibuat dan dicek belum memiliki `mayar_invoice_id`; adapter Mayar diisolasi dalam satu service layer untuk memusatkan logic ini. | Test: memanggil ulang proses pembuatan invoice untuk order yang sudah memiliki invoice tidak membuat invoice kedua. | Sedang |
| T-12 | Kebocoran PII lewat log | Log aplikasi mencatat email, nomor WhatsApp, atau payload pembayaran mentah secara lengkap. | Developer menambahkan `console.log`/logger tanpa masking saat debugging. | Paparan data pribadi pelanggan jika log diakses, dibagikan, atau ditampilkan saat screen-share. | Logging terstruktur dengan masking eksplisit untuk email dan nomor telepon; payload webhook mentah tidak dicatat lengkap — hanya field yang sudah disanitasi. | Review log sampel dari request test menunjukkan PII termask, bukan teks penuh. | Sedang |
| T-13 | Kebocoran secret lewat riwayat Git | Secret sempat ter-commit lalu "dihapus" di commit berikutnya, tetapi tetap ada di riwayat. | Commit tidak sengaja menyertakan file `.env`/`.dev.vars` atau nilai kredensial hardcoded. | Kredensial tetap dapat diambil dari riwayat Git meski file terbaru sudah bersih. | `.gitignore` mengecualikan seluruh file secret sejak commit pertama; secret scanning dijalankan terhadap seluruh riwayat sebelum deployment publik, bukan hanya commit terbaru. | Hasil secret scan riwayat Git penuh tidak menemukan pola API key/service role key. | Tinggi |
| T-14 | Ketidakstabilan URL webhook mendekati hari-H | Nama project Cloudflare Worker atau Pages diganti mendekati webinar, mengubah URL publik. | Perubahan konfigurasi deployment tanpa koordinasi tim mendekati H-0. | Webhook Mayar yang sudah terdaftar berhenti berfungsi; CORS allowlist menjadi tidak valid. | Nama project Cloudflare (Pages & Workers) dikunci sejak P4 (minimal H-7 hari) dan tidak diubah mendekati hari-H; setiap perubahan konfigurasi wajib diikuti retest CORS dan webhook. | Checklist deployment (`docs/PROJECT_CHECKLIST.md` Section 13) dikonfirmasi H-7 dan tidak ada perubahan nama project setelahnya. | Sedang |
| T-15 | Deployment tidak teruji mendekati hari-H | Perubahan kode/config dideploy ke environment demo publik tanpa direhearsal, mendekati atau saat webinar berlangsung. | Perubahan "kecil" yang dianggap aman didorong langsung ke demo tanpa smoke test ulang. | Kegagalan tak terduga saat live, tanpa waktu untuk debugging di depan audiens. | Tidak ada perubahan kode atau deploy baru saat sesi webinar berlangsung kecuali sudah direhearsal; checkpoint branch (`demo-start`/`demo-payment`/`demo-final`) tersedia sebagai jalur mundur aman. | Smoke test end-to-end diulang setelah setiap perubahan konfigurasi; dry run penuh dilakukan sebelum H-0. | Tinggi |
| T-16 | Retensi data setelah rehearsal/event | Data pelanggan uji (nama, email, nomor WhatsApp) dari sesi rehearsal dan webinar tersimpan tanpa batas waktu. | Tidak ada proses pembersihan data demo setelah acara selesai. | Penyimpanan PII yang tidak perlu, risiko kepatuhan/privasi jangka panjang. | Keputusan retensi data demo diterapkan setelah event, termasuk penghapusan/anonimisasi data pelanggan uji (lihat Open Question Q-06 di `docs/PROJECT_CHECKLIST.md`). | Catatan tanggal penghapusan/anonimisasi data pasca-event terdokumentasi dan dieksekusi. | Rendah |

## Prioritas Ringkas

- **Tinggi** — harus tuntas sebelum P10 (deployment publik) dan diverifikasi ulang sebelum setiap rehearsal: T-01, T-02, T-03, T-04, T-05, T-07, T-08, T-09, T-10, T-13, T-15.
- **Sedang** — harus tuntas sebelum rehearsal penuh (P11): T-06, T-11, T-12, T-14.
- **Rendah** — dapat diselesaikan setelah webinar selesai, tapi keputusannya harus sudah disepakati sebelum event: T-16.

## Status Keputusan

**Accepted.** Setiap mitigasi pada tabel di atas mengikat implementasi P5–P10 di `docs/PROJECT_CHECKLIST.md`. Perubahan pada threat model ini (menambah, menghapus, atau mengubah prioritas ancaman) memerlukan pembaruan eksplisit pada dokumen ini, bukan asumsi implisit saat coding.
